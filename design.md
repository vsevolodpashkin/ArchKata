# Design: Аналитическая платформа (NL → SQL → Отчёты)

Краткое описание ключевых архитектурных решений. Соответствующая диаграмма компонентов — `component-diagram.puml`.

---

## 1. Трансформация естественного языка в SQL (NL → SQL)

**Primary-путь:** `Core Service → LLM Adapter → LLM Provider`.

**Что подаётся в LLM:**
- Релевантный срез схемы DWH из `Metadata Repository` (таблицы, колонки, типы, описания, примеры значений) — подмножество отбирается по embedding-близости к NL-запросу.
- Few-shot примеры из каталога типовых запросов тенанта.
- Tenant context (роль, доступные домены) — **без фактических данных DWH**.

**Структурированный выход LLM** (строгий JSON):
```
{ "sql", "params", "intent", "confidence", "used_tables" }
```

**Защита и валидация перед выполнением SQL:**
- Парсер: разрешены только `SELECT` / `CTE`; whitelist ключевых слов; DDL/DML — отказ.
- Параметризация всех литералов — нейтрализация prompt-injection, пришедшего через данные.
- Подключение к DWH под read-only пользователем; `statement_timeout`; `LIMIT` на число строк.
- Cost-guard: отказ, если оценка сложности (joins × rows) выше порога.

**Fallback — NLP Service:**
- Активируется по circuit breaker (error-rate / latency LLM Provider выше порога за скользящее окно).
- Правилово-шаблонный парсинг + словари, привязанные к схеме через `Metadata Repository`.
- Гарантирует **деградацию сервиса**, а не полный отказ.

## 2. Кэширование запросов (Redis)

**Двухуровневый кэш:**

| Уровень | Ключ | Что хранит | TTL |
|---|---|---|---|
| **L1 — NL → SQL** | `nl2sql:{tenant}:{role}:{hash(query+schema_ver)}` | Сгенерированный SQL, confidence, использованные таблицы | 24 ч; инвалидация по `schema_ver` |
| **L2 — результат запроса** | `qry:{tenant}:{hash(sql+params)}` | Сериализованный результат | Real-time: 30 с · Агрегаты: 1 ч · Отчёты: 24 ч |

**Защита от cache stampede:** single-flight — при промахе пересчитывает только первый запрос, остальные ждут и читают уже записанный ключ.

**Инвалидация:**
- **Schema-driven:** bump `schema_ver` в `Metadata Repository` → старые L1-ключи становятся нечитаемыми (новый ключ).
- **Event-driven:** CDC из DWH → точечный `DEL` L2-ключей по затронутым таблицам.
- **Per-tenant flush:** при изменении прав пользователя или выписке тенанта из сервиса.

**Имена ключей всегда включают `tenant_id`** — физически невозможно прочитать данные чужого тенанта (см. §5).

---

## 3. Проверка ролевой модели (RBAC)

**Внешний RBAC Service** — единый источник прав. Авторизация применяется в **трёх точках**, не в одной:

1. **Frontend Service** — аутентификация пользователя и фильтрация UI (видимость вкладок, кнопок, пунктов меню).
2. **Core Service** — авторизация запросов: в сгенерированный SQL **инжектируются `WHERE`-предикаты** по атрибутам роли (регион, департамент, проект, категория клиента). Это гарантирует, что пользователь физически не увидит чужие строки.
3. **Reporting Service** — фильтрация шаблонов отчётов; запрет выгрузок по недоступным доменам.

**Кэш прав:** Redis, ключ `rbac:{user_id}:{tenant_id}`, TTL 5 мин. Инвалидация — по событию `role_changed` от RBAC (push-уведомление).

**Аудит:** каждый запрос логируется с `user_id`, `tenant_id`, `sql_hash`, `row_count`, `duration_ms`. Цель — расследование инцидентов и соответствие регуляторным требованиям.

## 4. Multi-tenant режим

**Идентификация тенанта:** `tenant_id` извлекается из токена пользователя и валидируется RBAC. Протаскивается через все внутренние вызовы (HTTP-header `X-Tenant-Id` + gRPC-metadata).

**Изоляция в DWH — выбрана shared schema с `tenant_id`-колонкой:**
- Дешевле, чем schema-per-tenant, и проще в эксплуатации.
- Совместимо с Row-Level Security на уровне DWH (двойной пояс безопасности).
- Требует дисциплины: **любая выборка обязана содержать `WHERE tenant_id = :tenant_id`**.

**Квоты тенанта (enforce на edge / Core Service):**
- Rate limit по NL-запросам (RPS).
- Бюджет `query_cost` (rows_scanned за минуту).
- Concurrency-limit на тяжёлые отчёты.
- Отдельные алерты по превышению.

**Наблюдаемость:** дашборды Grafana разнесены по `tenant_id`; в логах и трейсах `tenant_id` — обязательный лейбл.

## 5. Изоляция данных (Defense in depth)

| Слой | Механизм |
|---|---|
| **Сетевой** | Per-tenant DB-connection pool; в перспективе — отдельные VPC / subnet на крупных тенантов |
| **Авторизация** | RBAC на каждом запросе (см. §3); атрибуты роли → SQL-WHERE |
| **БД** | Read-only пользователь; Row-Level Security policy `USING (tenant_id = current_setting('app.tenant_id'))` |
| **Кэш** | Префикс ключа по `tenant_id`; чужой ключ физически недоступен |
| **LLM-промпт** | Никогда не содержит строки DWH — только метаданные схемы и фильтры роли |
| **Логи / трейсы** | `tenant_id` в каждой записи; доступ к сырым логам ограничен ops-ролью и пишется в append-only |

**Главный принцип:** **Core Service — единственный компонент, который генерирует SQL**. Произвольный SQL от пользователя или внешней системы отвергается на входе. Это убирает целый класс инъекций и гарантирует, что правила изоляции применяются всегда, а не «когда не забыли».

---

## Сводка принятых решений

| Решение | Выбор | Обоснование |
|---|---|---|
| NL → SQL primary | LLM с метаданными + few-shot | Лучшее качество на неоднозначных запросах |
| NL → SQL fallback | Rule-based NLP Service | Деградация вместо отказа; нулевая стоимость при срабатывании |
| Кэш | Redis, 2 уровня | NL→SQL дорогой, результаты тяжёлые — оба уровня оправданы |
| Изоляция в DWH | Shared schema + `tenant_id` + RLS | Баланс стоимости и безопасности |
| Авторизация | RBAC-сервис + SQL-WHERE injection | Фильтрация на уровне данных, а не UI |
| Безопасность SQL | Core Service — единственный генератор | Устраняет класс атак, упрощает аудит |
